日期：2026-08-27

## 一、结论先行

技术上可行，但**最初设想的切入点（智慧交通信号）已被现有 mod 占掉**，需要重新定位。

三条结论：

1. **官方 toolchain 成熟**，C# + React 的工程范式清晰，不需要 BepInEx 那套非官方路线。
2. **游戏原生就有"感知层"数据**（`Game.Net.LaneFlow` 等），不需要自己造传感器模拟。
3. **自适应信号配时已经有成熟实现**（TrafficLightsEnhancement），重做没有意义。差异化必须在别处。

## 二、Toolchain 现状

官方 Modding Toolchain 内置在游戏 Options → Modding 里，会自动检测和安装依赖。

| 依赖 | 要求 | 谁装 |
|---|---|---|
| IDE | VS2022 ≥17.8（C#）/ VSCode ≥1.86（UI） | 手动 |
| Unity Editor | 2022.3.7f1（需 Unity 账号 + license） | toolchain 自动 |
| .NET SDK | 最低 6，推荐 8 | toolchain 自动 |
| Node.js | ≥18（仅 UI mod） | toolchain 自动，装 20.11 |

关键环境变量（Steam 版默认）：

```
CSII_INSTALLATIONPATH = C:\Program Files (x86)\Steam\steamapps\common\Cities Skylines II
CSII_USERDATAPATH     = C:\Users\<user>\AppData\LocalLow\Colossal Order\Cities Skylines II
CSII_LOCALMODSPATH    = %CSII_USERDATAPATH%\Mods
CSII_TOOLPATH         = %CSII_USERDATAPATH%\.cache\Modding
```

构建流程：MSBuild + Roslyn → AfterBuild 跑 `ModPostProcessor.exe`（IL 后处理 + Burst 编译成 native）→ 自动拷贝到 `CSII_LOCALMODSPATH`。

开发期有用的启动参数：
- `--developerMode` — Tab 键开发者菜单
- `--uiDeveloperMode` — Chrome DevTools 挂在 `http://localhost:9444`，UI 支持热重载

本地禁用某个 mod：文件夹名前加 `.`（`Mods/.MyMod`）。

技术栈事实：Unity 2022.3.7f1，Mono，.NET Standard 2.1，`net472` 目标框架。UI 是 Coherent Labs Gameface 跑的 React + TypeScript（不是完整浏览器，CSS 支持受限）。

## 三、三个参考 mod 的实测发现

已 clone 到 `_reference/`，读过源码。

### 3.1 TrafficLightsEnhancement（slyh）——最重要的发现

**它已经做了自适应信号控制。** 核心组件 `CustomPhaseData` 里有：

```csharp
public float3 m_CarFlow;            // 近三个周期的车流
public ushort m_CarLaneOccupied;    // 车道占用
public float  m_WeightedWaiting;    // 加权等待
public float  m_TargetDuration;     // 动态目标时长
public ushort m_MinimumDuration;    // 2s
public ushort m_MaximumDuration;    // 300s
```

流量是怎么采出来的（`CustomStateMachine.CalculateFlow`）：

```csharp
// 游戏原生组件 Game.Net.LaneFlow 带累计量，差分即得流量
newDistance = math.lerp(laneFlow.m_Distance, laneFlow.m_Next.y, timeFactors);
newDuration = math.lerp(laneFlow.m_Duration, laneFlow.m_Next.x, timeFactors);
diffDistance = newDistance - oldDistance;
customPhaseData.m_CarFlow.x += totalDiff * (64f / (float)diffFrame); // 64 帧一个信号 tick
```

**含义：**
- 游戏本身就在记录每条车道的累计通行距离和耗时。城市级交通感知数据是现成的，这是我们能站上去的地基。
- 但"给路口装感应器、按车流配时"这件事已经有人做完且做得不错，我们不该重做。

**接管游戏系统的手法**（`Mod.cs`）值得照搬：

```csharp
// 1. 给自己的实体打标记组件，把原版 system 的 query 排除掉
noneList.Add(ComponentType.ReadOnly<Components.CustomTrafficLights>());
Utils.EntityQueryUtils.UpdateEntityQuery(m_TrafficLightSystem, "m_TrafficLightQuery", noneList);

// 2. 把自己的 system 插在原版之前
updateSystem.UpdateBefore<PatchedTrafficLightSystem, Game.Simulation.TrafficLightSystem>(
    SystemUpdatePhase.GameSimulation);
```

这是比 Harmony patch 更干净的做法——用 ECS 的 query 过滤实现共存，而不是替换方法。原作者还专门设计了"兼容模式"让多个同功能 mod 并存。

### 3.2 InfoLoom（Infixo）——诊断型的参照

纯读取、不改任何游戏系统、不动存档。用 `IJobChunk` 遍历 `Game.Citizens.Citizen` / `Worker` / `Student` 等组件做统计，再推到 UI。

暴露出来的游戏 namespace（对我们摸 API 很有价值）：
`Game.Agents` / `Game.Buildings` / `Game.Citizens` / `Game.Objects` / `Game.Simulation` / `Game.Net` / `Game.Tools` / `Game.Debug`

**注意：它用的 Gooee UI 框架是第三方的，且已过时。我们应该用官方 `Colossal.UI.Binding`。**

### 3.3 C# ↔ React 数据通道（官方方式）

TLE 用的是官方 API，模式很清楚：

```csharp
// C# 侧：三种绑定
AddBinding(new GetterValueBinding<string>("C2VM.TLE", "GetMainPanel", GetMainPanel));  // 拉取
AddBinding(new ValueBinding<int>("C2VM.TLE", "GetActiveIndex", -1));                    // 推送
AddBinding(new CallBinding<string, string>("C2VM.TLE", "CallMainPanelSave", CallSave)); // UI 调 C#
```

更新节流也有现成范式（避免每帧刷 UI）：

```csharp
if (updateFrame.m_Index == SimulationUtils.GetUpdateFrameWithInterval(
        m_SimulationSystem.frameIndex, 4, 16)) {
    m_UISystem.SimulationUpdate();
}
```

## 四、重新定位的建议

### 为什么原方案要改

「智慧交通信号」是最直觉的切入点，但 TLE 已经做到了单点最优——每个路口自己感应车流、动态配时。我们再做一遍，最好的结果也只是复制。

### 差异化在哪

TLE 做的是**单点优化**：一个路口只看自己的车流。它不知道也不关心车为什么会来、堵在这里对城市别处意味着什么。

CS2 的真实痛点是**模拟不透明**：需求为什么归零、这栋楼为什么被废弃、这条路为什么突然堵了——数据都在 ECS 里，但散落在几十个互不相关的 system 中，玩家只能靠猜。

**Urban Brain 的定位应该是跨域因果诊断，而不是数值优化。**

举例，一条完整的解释链：

> 这个商业区在废弃 → 因为货运到达率低 → 因为卡车绕行了 3.2km → 因为主干道 17:00–19:00 饱和 → 因为工业区和住宅区的通勤时段完全重叠

这条链上的每一环，数据都在游戏里，但**没有任何一个现有 mod 把它们串起来**。这正是 LLM 相对于规则引擎有真实优势的地方：跨域关联推理，而不是数值最优化——后者用传统算法反而更好。

### 与「智慧城市」概念的咬合

之前聊的"感知层要花钱铺、且累积隐私代价"的设计，在这个定位下反而更自然：

- 你的**诊断精度**取决于你铺了多少数据基础设施
- 没铺传感器 → 只能看到"这条路很堵"
- 铺了 → 能看到"17:30 左转相位不足"
- 铺满 → 能看到完整因果链
- 但监控度累积负面效应（市民满意度、特定人群迁入意愿）

这样 AI 不是外挂式的作弊器，而是玩家在游戏内投资换来的能力。

## 五、架构建议：三层解耦

关键设计原则：**采集层和推理层必须解耦**。

```
┌─────────────────────────────────────────┐
│ L3  推理层（可插拔）                       │
│     本地 LLM / 云 API / 纯规则引擎          │
├─────────────────────────────────────────┤
│ L2  快照层：结构化城市状态 JSON             │
│     ← 这是稳定契约，也是天然的调试断点        │
├─────────────────────────────────────────┤
│ L1  采集层：ECS 查询 + 时序聚合             │
│     Game.Net.LaneFlow / Citizens / ...   │
└─────────────────────────────────────────┘
```

这么分的三个理由：

1. **风险隔离** —— 如果联网方案被 Paradox 审核卡住（见下），L1+L2 仍然是一个有价值的诊断 mod，可以独立发布。
2. **可调试** —— L2 的 JSON 快照可以直接 dump 到文件，我在没有游戏的机器上也能对着真实数据迭代 prompt 和推理逻辑。这对我们的协作方式至关重要。
3. **可替换** —— 推理层换成本地 Ollama、云 API 或纯规则，上层 UI 不用动。

## 六、风险与未知

| 风险 | 判断 | 缓解 |
|---|---|---|
| **联网政策** | Paradox Mods 未公开说明是否允许 mod 发起网络请求。CS1 有先例（Ellinox AI Guide），CS2 未找到先例。 | **已定：云 API + 玩家自填 key**。key 存游戏用户数据目录，不入仓库；明确告知发送内容；核心诊断功能不依赖网络 |
| **Burst 代码不可 patch** | 官方明说：Burst 编译后变成非托管代码，Harmony 只能 patch 托管代码 | 用 TLE 的 ECS query 过滤法，不用 Harmony |
| **游戏更新破坏兼容** | ECS 组件字段没有稳定 API 保证 | 采集层集中封装，把破坏面收窄到少数文件 |
| **性能** | 城市级全量扫描不能每帧做 | 用 `GetUpdateFrameWithInterval` 节流，重活放 `IJobChunk` |
| **未知：具体组件定义** | 目前只知道 namespace 和少数字段名 | **需要你导出程序集**（见下） |

另外一个非技术风险：LLM 输出不稳定。诊断说错了比不说更糟。设计上要让 AI 只在**有数据支撑**时开口，并且始终把原始数据一起展示——玩家能自己验证。
