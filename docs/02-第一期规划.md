# 第一期规划：AI 路口大脑

日期：2026-08-27

---

## 定位变更

**本项目为个人自用，不公开分发。** 这带来一系列简化：

| 原约束 | 自用后 |
|---|---|
| Paradox Mods 审核（联网政策不明） | 不适用，API 随便调 |
| 与其他 mod 共存（兼容模式） | 不需要，装我们的就不装 TLE |
| 多语言、发布配置、用户友好 | 不需要，中文即可 |
| 不能借用他人代码 | 可直接移植参考实现 |

最终目标是「城市大脑」，第一期先做**路口与信号**这一块。

---

## 一期目标

**选中路口 → 看到实测流量 → AI 给出配时与转向方案 → 一键应用 → 信号立即生效。**

再往上一层：全城扫描，列出最该改的 N 个路口。

一期包含两类控制能力：

1. **信号配时** —— 相位划分、各相位时长
2. **转向规则** —— 每条车道能否左转 / 直行 / 右转 / 掉头

其中转向规则一期**可以不接 AI，手动勾选即可**；信号配时是 AI 的主战场。

---

## 我们和现有 mod 的关系

必须清楚：TLE 和 Traffic 已经覆盖了大部分**执行层**能力。

- TLE：感应式配时（按实测流量动态调整绿灯长度）+ 自定义相位
- Traffic：车道连接器、路口优先级

**我们的价值全部在决策层。** 它们是执行机构，我们做大脑。

具体增量：

| | 现有 mod | Urban Brain |
|---|---|---|
| 绿灯该延长还是缩短 | ✅ 运行时反馈控制 | 沿用 |
| 这个路口该用几相位、怎么分组 | ❌ 玩家手动设计 | **AI 生成** |
| 邻近路口绿波协调 | ❌ 各自独立 | **AI / 算法协调** |
| 全城哪些路口该改 | ❌ 玩家自己找 | **批量扫描** |

## 技术地基（已验证）

调研阶段读过源码并交叉验证的部分：

| 能力 | 参考实现 | 规模 | 风险 |
|---|---|---|---|
| 流量采集 | `Game.Net.LaneFlow` 差分 | 已验证 | 🟢 |
| 接管信号系统 | TLE `PatchedTrafficLightSystem` | ~1200 行 | 🟡 |
| 车道转向控制 | `CommonLibraries/CustomLaneDirection` | 250 行 | 🟢 |
| C# ↔ React 通道 | `Colossal.UI.Binding` + `cs2/api` | 有完整模板 | 🟡 |
| UI 工程 | `TLEFrontend`（React18+TS+webpack） | 可直接抄配置 | 🟡 |

**接管手法**（比 Harmony 干净，且 Burst 代码无法被 Harmony patch）：

```csharp
// 1. 给自己接管的实体打标记组件，把原版 system 的 query 排除掉
noneList.Add(ComponentType.ReadOnly<UrbanBrainControlled>());
EntityQueryUtils.UpdateEntityQuery(m_TrafficLightSystem, "m_TrafficLightQuery", noneList);

// 2. 把自己的 system 插在原版之前
updateSystem.UpdateBefore<OurTrafficLightSystem, Game.Simulation.TrafficLightSystem>(
    SystemUpdatePhase.GameSimulation);
```

**转向规则的数据形态**（每车道四个开关，够用且简单）：

```csharp
m_BanLeft / m_BanStraight / m_BanRight / m_BanUTurn
```

不做 Traffic 那种任意车道对任意车道的连线编辑——那 6000 行差距几乎全在拖拽交互 UI 上，对 AI 决策毫无帮助。

## 里程碑

| | 内容 | 风险 | 需要实机测试 |
|---|---|---|---|
| **M1** | **写入验证**：接管信号，绿灯固定 60 秒，肉眼可见 | 🔴 最高 | ✅ |
| **M2** | 读取：路口几何 + 各流向实测流量，导出 JSON | 🟢 | ✅ |
| **M3** | 转向规则执行层：禁用某流向并生效 | 🟡 | ✅ |
| **M4** | 规则版方案生成（对照组，不用 AI） | 🟢 | ❌ 本地 |
| **M5** | AI 决策层：生成方案 + 理由 | 🟡 | ❌ 本地 |
| **M6** | UI 面板：选路口 / 看方案 / 勾选应用 | 🟡 | ✅ |

### 为什么 M1 排第一

不管一期范围多大，「**能不能在不搞坏游戏的前提下写入控制**」这个问题必须最先回答。

M1 功能上毫无用处（所有路口绿灯 60 秒，纯属添乱），但它一次性验证了：编译链、mod 加载、ECS 查询接管、写入生效、存档兼容。通了，后面都是在已验证地基上加东西；不通，一期要重新设计。

### 为什么 M4 不能跳过

M4 是 M5 的**对照组**。

如果规则引擎能找出的方案，AI 也只能给出同样的东西，那 AI 就没有带来增量。先有对照组，一期结束时才能诚实判断 AI 到底值不值得接。

### M2 的额外作用

M2 导出的 JSON 让 Claude 能在**没有游戏的机器上**独立迭代 M4/M5。这是 M4、M5 标注「不需要实机测试」的原因——那两步可以完全在本地完成，不占用晚上的测试时间。

## 一期成功标准

可证伪的那种：

> **AI 给出的配时方案，在至少一个真实拥堵路口上，效果优于规则引擎的方案，且理由站得住。**

做不到就说明要么数据维度不够，要么这个方向不成立——那就该改方向，而不是继续加功能。

## 明确不做

- 不做 Traffic 式的拖拽车道连线编辑器
- 不做与其他 mod 的兼容模式（自用，二选一）
- 不做多语言、不上架
- 不做实时自动接管（一切由玩家点击触发）
- 不碰「智慧城市玩法系统」（感知层成本、隐私代价那套 —— 属于后续，且依赖一期验证结果）
